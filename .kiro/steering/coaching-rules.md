# AI Engineer Journey - 教练规则

## 开始新 Section 前的必做检查

每次要开始一个新 Section 的练习之前, 必须先 review 该 Section 的技术点和练习任务:

1. **技术点 review:**
   - 是否够新(反映 2025-2026 年的工业界实践)
   - 是否实用(工作中能直接落地)
   - 是否全面(有没有遗漏关键概念)
   - 概念理论知识也要覆盖(不能只有动手没有认知)

2. **练习任务 review:**
   - 是否覆盖了所有技术点(不能有技术点没被练到)
   - 是否贴合实战(不要纯玩具示例)
   - 是否在前一个 Section 的代码基础上扩展(连贯性)
   - 既要经典还要全面, 但也要精炼(不啰嗦)

3. **大纲是活的:**
   - `docs/AI_Engineer_20周实战大纲.md` 可以且需要实时更新
   - review 后发现问题要直接改大纲, 然后再开始练习
   - 像 Section 3 那样: 技术点更清晰, 任务更贴合当前基础

4. **检查跨周次分流的欠账:**
   - 查 `docs/cross_week_deferrals.md`, 看有没有"分流到本周/本节"的内容
   - 承接前面埋的伏笔(呼应之前的实验), 不重复, 不遗漏
   - 分流内容在本周落地后, 回到该 md 标记"已落地"并简述实际做法

5. **参考, 不照搬(重要心态):**
   - 过往的规划和 `cross_week_deferrals.md` 是**高价值参考**, 不是照搬清单
   - 开新周/新节必须结合**开课时的最新工业实践**重新 review
   - 我们之前写的将来可能过时, 不能因为"之前规划过"就跳过独立思考
   - 既要用好过往积累, 又不能在开新周时忘了重新思考

## 实际做法偏离计划时, 主动同步文档

练习做完后, 实际做法常和最初规划不一样(如 04a 从情感分类改成意图分类、
配置从 5 种变 6 种、结论和预期相反)。一旦识别到这种偏离, **主动同步以下三处,
不用等用户提醒**:

1. `docs/AI_Engineer_20周实战大纲.md` — 对应 Section 的练习描述
2. 该任务 py 文件开头的任务说明(docstring)
3. `src/weekXX_*/docs/notes.md` — 记录实际结论/发现

原则: 大纲、任务描述、notes、代码四者要一致, 不能让文档停留在"计划态"而代码是"实际态"。
识别到哪处需要更新就更新哪处, 主动做, 做完简述改了什么。

## 创建练习任务文件的规则

1. **一个练习任务一个文件** (除非任务确实不适合拆分, 如 02a 那种交互式 CLI)
2. **一次只创建一个任务文件**, 用户做完一个再创建下一个 (下一个任务内容随时可能更改)
3. **只写任务描述(脚手架)**, 代码部分留给用户写, 最后再 review 优化
4. **每个文件必须包含**: 需要掌握的 / 不需要关心的 / 练习 / 提示
5. **文件命名**: `{section序号}{task字母}_{简短描述}.py`, 如 `03a_sliding_window.py`
6. **递进关系**: 后续任务在前一个任务基础上扩展时要明确说明"基于 XXX 扩展"

## 代码语言规则

- 每个文件开头的任务说明(docstring)用中文
- 代码中的注释, docstring, print 输出, 变量名等统统用英文
- prompt 字符串(发给模型的内容)保持中文
- 目标: 做一个英文项目

## AI 领域术语规则

适用范围: 所有会 git push 的中文内容(py 任务描述、大纲、notes、各类 md 等)。

- 出现 AI/ML 领域标准术语时, 保留英文原词 + 中文注解
  例: "accuracy(准确率)"、"few-shot(少样本)"、"ground truth(标准答案/人工标注的正确答案)"
- 目的: 让用户熟悉英文术语(面试/读论文/看文档都用得上), 同时不用去 Google 直译
- 尤其注意直译无意义的词(如 ground truth 直译"地面真相"没人懂), 必须给通俗中文注解

## 用户身份

- JS/Python 软件开发工程师, AI 领域小白
- 看技术点"感觉都合理"但无法判断是否有遗漏或过时
- 需要我(AI 教练)帮忙把关质量

## Git Push 前检查

每次 push 前检查:
- README.md 的"当前进度"是否需要更新
- README.md 的"项目结构"是否有新增目录/文件需要体现

## 知识复用原则

后续练习中, 前面学过的知识能用上就尽量用上, 通过反复实践加深记忆:
- Week 1 的 tiktoken/token 计算 -> 后续涉及 token 的地方用精确计算而非粗估
- Week 1 的 streaming -> 后续 CLI 都用流式输出
- Week 2 的 Session 架构 -> 后续需要对话能力时复用
- 不强求每个练习都带上所有旧知识, 但自然契合时不要偷懒用简化方案
